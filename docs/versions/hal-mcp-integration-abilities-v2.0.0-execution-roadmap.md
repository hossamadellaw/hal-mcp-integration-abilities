## 1. القرار التنفيذي وحدود النطاق

تطوير الإضافة القائمة إلى Standard Plugin عامة لمواقع WordPress، مع إعادة استخدام Abilities API وتقسيم includes/abilities الحالي. تضاف واجهة أوامر وإعدادات داخل WordPress، واتصالات مزودي نماذج، وطلبات تغيير تعتمدها الإدارة، واكتشاف للبيئة، وتكاملات محتوى وصفحات وSEO وترجمة. يبقى MCP الرسمي قناة للبرامج الخارجية، وتطبق عليه قواعد الصلاحيات والاعتماد نفسها.

لا يعاد بناء المشروع في طبقات Services/Repository أو إطار إضافات داخلي أو حاويات حقن اعتماديات. لا Gateway أو Hub، ولا خادم Node دائم، ولا قاعدة متجهات أو نظام وكلاء متفرع أو منصة أتمتة. الملفات الجديدة أدناه وحدات وظائف مباشرة بسبب المتطلبات، وليست طبقات تمرير.

الأولوية لتعليمات المالك الحالية على أحكام الوثائق القديمة: حظر النشر الدائم يستبدل بالنشر بعد اعتماد الإدارة؛ الارتباط بموقع ولغة واحدة يلغى؛ MU يتحول إلى standard؛ التقارير القديمة أدلة تاريخية تحتاج مقارنة بالكود وليست قائمة متطلبات تلقائية.

**الفحص الحي وstaging ليسا شرط إغلاق لأي بند أو مرحلة أو للقائمة.** فحوص الوثيقة والتنفيذ المقترحة محلية محدودة بحسب الأدوات المتاحة. لا تُنشأ بيئة إضافية ولا تثبت اعتماديات للاختبار دون تفويض تنفيذ لاحق. تعذر تشغيل تكامل خارجي يُذكر بحده، ولا يوقف إكمال الملفات المستقلة ولا يُستبدل بادعاء نجاح تشغيلي.

لا يعني ذلك إغلاق ميزة غير مكتوبة باعتبارها مكتملة: يميز التسليم بين «مُنفذ ومراجع محليًا» و«مُتحقق تشغيليًا». لا يلزم الثاني لإنهاء القائمة المطلوبة، ولا يجوز ادعاؤه من الأول.

## 4. المعمارية الدنيا والقرارات العملية

### 4.1 الملفات والاعتماديات

- يبقى المجلد hal-mcp-abilities/ بمحتواه؛ لا نقل جماعي ولا تغيير أسماء القدرات hal/* دون حاجة.
- يتحول المحمّل الجذري إلى hal-mcp-integration-abilities.php. يبقى hal-mcp-abilities/hal-mcp-abilities.php bootstrap داخليًا بلا ترويسة إضافة ثانية.
- واجهة الإدارة PHP وJavaScript/CSS باستخدام مكونات WordPress الموجودة؛ لا إطار frontend أو build pipeline جديد لمجرد صفحة الإعدادات.
- الاتصال بالمزودين عبر WordPress HTTP API. لا SDK لكل مزود. ملف providers.php يضم تعريف المزود والتحويل بين الصيغ المدعومة، ويستخدم http-client.php للنقل المشترك.
- MCP Adapter الرسمي إضافة خارجية مكتشفة، لا نسخة SDK جديدة مضمنة. غيابه يعطل القناة الخارجية فقط، ما دامت Abilities متاحة للواجهة الداخلية.
- خط الأساس لـAbilities هو WordPress 6.9. المرجع التقني لقناة MCP في هذه الوثيقة هو Adapter v0.6.1 ومواصفته المعلنة 2025-11-25؛ لا يخلط مع توثيق MCP أحدث لم يثبت توافقه مع هذا الإصدار. PHP الأدنى يُشتق من الشيفرة والاعتماديات عند التنفيذ، ولا ينسخ إصدار استضافة سابقة. PHP المحلي المرصود 8.4.13 أداة فحص متاحة، وليس دليلًا على جميع الإصدارات.
- اعتماد التحديث الوحيد الجديد المطلوب من المرجع هو PUC عبر Composer والقفل. Composer أداة بناء؛ لا يلزم وجوده على موقع العميل.
- لا تختار لغات أو إضافة SEO ثابتة في الإعداد الافتراضي. يسمح للمدير بتصحيح الاكتشاف أو اختيار المزود دون تعديل كود.

مرجع خط الأساس وإتاحة الأدوات: [Abilities API](https://developer.wordpress.org/apis/abilities-api/) و[Adapter v0.6.1](https://raw.githubusercontent.com/WordPress/mcp-adapter/v0.6.1/README.md). الأرقام هنا حدود مرجعية وليست ادعاء تشغيل.

### 4.2 مسار العمل المشترك

الأمر الداخلي → providers.php → اقتراح استدعاء أداة → runner.php → القدرة المسجلة عبر Abilities → صلاحيات العنصر وسياسة التغيير → تنفيذ مسموح أو طلب اعتماد → نتيجة وسجل مختصر.

البرنامج الخارجي → MCP Adapter → قدرات hal/* نفسها → السياسة نفسها. لا تُنفذ الكتابة في JavaScript أو داخل عميل HTTP، ولا يمر طلب الأداة مباشرة إلى دالة WordPress من اسم ولّده النموذج.

الموافقة من صفحة الإدارة → تحقق جلسة بشرية مخولة وnonce → طلب تغيير محفوظ وإصدار payload مطابق → تطبيق محدد وتسجيل النتيجة. لا تُعرض approve/reject كقدرات MCP أو أدوات للنموذج، ولا تقبل قيمة approved في مدخل النموذج.

لا تتخذ الأداة لنفسها صلاحيات المستخدم Administrator بمجرد أن الإداري فتح شاشة الأوامر. إعدادات الإدارة واعتمادها منفصلان عن صلاحيات مسار النموذج؛ الأوامر الإدارية العامة غير المدرجة في محتوى النسخة تُعرض كطلب للإدارة لتنفيذه خارج الأداة، دون إضافة أدوات SQL/PHP أو تثبيت إضافات أو إدارة مستخدمين لهذا الإصدار.

### 4.3 طلبات التغيير والاعتماد

- تخزن في نوع محتوى داخلي واحد hal_mcp_request، غير عام وغير ظاهر في REST العام أو البحث أو الترجمة أو أدوات المحتوى. لا قاعدة بيانات خدمات جديدة.
- حقول الطلب: kind، العملية، site/blog ID، منشئ الطلب، معرفات الأهداف، حقول التغيير المنقحة، هوية المحرر/التكامل والنسخة، اللغة، بصمة الأصل وبصمة المقترح، حالة الطلب، المعتمد والتوقيت، نتيجة التطبيق. يمكن استعمال kind=run لحالة المحادثة القصيرة وإكمال الخطوات دون إضافة مخزن ثان.
- دورة الحالة: pending → approved → applying → applied؛ بدائل rejected/failed/conflict. تعديل المقترح يعيد الحالة إلى pending ويلغي الاعتماد السابق.
- التنفيذ المباشر يقتصر على draft/auto-draft المسموح بها وعلى العملية التي لا تؤثر في أصل منشور. publish/future/private والحالات المخصصة غير المعروفة تعامل كمحمية إلى أن تُعرف آثارها. لا يستعمل الشرط الحالي «ليس publish» تصريحًا عامًا.
- الموافقة مرتبطة بنفس المحتوى والحقول واللغة والأهداف؛ تغيير السعر أو SEO أو العلاقات أو التصميم بعد الموافقة لا يرثها.
- تطبق صلاحيات الطالب على طلب التغيير وصلاحيات المعتمد اللازمة للنشر/التعديل عند التطبيق، وتُرفض الطلبات التي تعدل بيانات خارج نطاق التفويض. لا يُغيَّر دور الطالب إلى Administrator.
- يمنع التكرار بواسطة request ID وحالة تطبيق محفوظة وقفل قصير لكل طلب/هدف ضمن الإضافة؛ يعاد فحص بصمة الأصل قبل الكتابة. إذا تغير الأصل فلا overwrite صامت: تعاد المعاينة والاعتماد.
- لا يدعي القفل حماية ذرية من كل إضافة أخرى تكتب خارج هذا المسار. تحفظ حقول التعديل فقط، وتُلتقط التعارضات الممكنة، ويذكر الحد بدل بناء transaction engine.
- يحفظ قبل التطبيق snapshot للحقول والروابط التي ستتغير فقط. الاسترجاع تغيير مخول جديد لا يستبدل تعديلات أحدث بلا مقارنة. فشل منتصف عملية متعددة الحقول يسجل ما تم وما فشل، ولا يعاد التطبيق تلقائيًا على نحو يكرر الآثار.
- المقترحات القديمة الموجودة كمقالات/منتجات تبقى محفوظة ولا تُنشر أو تُحذف أو تُعتمد آليًا. الطلبات الجديدة تستخدم التخزين الداخلي.

### 4.4 اكتشاف البيئة والتكامل

- الجرد الأول محلي بعد اكتمال تسجيل الأنواع والإضافات؛ ليس أثناء تحميل ملف قبل توفر WordPress.
- يشمل إصدار WP/PHP، الموقع المفرد/الشبكة، القالب، معرف الإضافة وإصدارها وحالتها، المحررات وكتلها/عناصرها المتاحة، أنواع المحتوى والتصنيفات والحقول المكشوفة رسميًا، WooCommerce وأنواع المنتجات، SEO، نظام اللغات واللغات المهيأة، والصلاحيات ذات الصلة.
- لا يُرسل الجرد الكامل أو الأسرار أو بيانات المستخدمين للمزود افتراضيًا؛ ترسل فقط المعلومات والمحتوى اللازمان للمهمة والمسموح بقراءتهما.
- تحفظ نتيجة موجزة لكل موقع على حدة، مع invalidation عند تغير الإضافات/القالب/اللغة، وزر إعادة اكتشاف. لا فحص ثقيل بكل طلب ولا scheduler جديد.
- تعرض القدرات على مستوى العملية: متاح، متاح جزئيًا، يحتاج إعدادًا، غير متحقق. المعرفة باسم الإضافة لا تمنحها إذن تنفيذ أدواتها.
- integrations.php يحتفظ بسجل callbacks بسيط مسمى، بوظائف discover/read/validate/apply عند الحاجة. لا أصناف أساسية ووراثة وإطار تحميل آلي. لا إنشاء ملفات plugin عشوائية بواسطة النموذج.
- الواجهات الرسمية المسجلة قد تعطي قابلية قراءة أو كتابة؛ تسجيل قدرة طرف ثالث وحده لا يكفي لاستدعائها. يحدد الربط نوع أثرها وصلاحياتها ومخططها، وتمر الكتابة عبر طلب التغيير. القدرات غير المصنفة لا تُمرر خامًا.
- المواقع متعددة المواقع تستخدم خيارات وجداول وسياق الموقع الحالي؛ لا switch_to_blog من مدخل نموذج ولا صلاحيات عابرة للمواقع. التحميل على الشبكة لا يفرض جرد كل المواقع دفعة واحدة. غياب إثبات تكامل الشبكة يوضح كحد تحقق دون تعطيل الاستخدام المحلي.
